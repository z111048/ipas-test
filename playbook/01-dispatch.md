# 01 — 模型調度守則（指揮官不下場）

適用對象：主對話模型（任何等級，包含 Sonnet）。目標：主對話的 context 只裝「決策需要的結論」，
不裝原始資料。所有規則都給了數字判準，照做即可，不需要品味。

## 0. 總原則：主對話是指揮官

主對話**只做**：理解需求、拆解任務、派工、讀回報結論、做決策、對使用者回報。
以下工作**一律派 subagent**，主對話只收結論：

| 任務型態 | 判準（達到任一條就派工） | 派給誰 |
|---|---|---|
| 讀檔/掃 repo | 要讀 >3 個檔案，或任一資料 JSON >50KB，或「不確定在哪個檔」 | `Explore`（唯讀） |
| 查網頁/文件 | 需要 >1 次 WebSearch/WebFetch 往返 | `general-purpose` |
| 批次改檔 | 同型修改 >3 個檔案 | `general-purpose` |
| 設計實作方案 | 動 >2 個模組，或有架構取捨 | `Plan` |
| 驗收 | 一律（見 §4 驗證不自驗） | fresh `general-purpose` |

主對話**可以自己做**（不必派工）：單一 Grep/Glob 查找、已知路徑的小檔（<200 行）閱讀、
單檔小修改（<50 行 diff）、跑指令看輸出、與使用者對話。
派工過度也是浪費——一個 30 秒能自己查完的事，不要開 agent。

**大檔切片法**（自己處理資料 JSON 時）：
```bash
ls -la <file>                                # 先看大小，>50KB 不整檔讀
jq '.questions | length' file.json           # 先看結構規模
jq '.questions[] | select(.id=="s1c1q3")' file.json   # 只取目標
grep -n "關鍵字" file.json | head             # 定位行號後用 Read offset/limit
```

## 1. 派工三件套（缺一不派）

每個 subagent prompt 必含三段（模板見 `03-templates.md`）：

1. **目標與動機**：要達成什麼＋為什麼（動機讓 agent 在邊角情況做對取捨）。
   壞例：「看一下 questions 目錄」。好例：「找出 subject1_questions.json 中所有缺
   `card` 欄位的題目 id，因為要補跑 enrich，需要精確清單來估 API 費用」。
2. **驗收條件**：可機械檢查的完成定義。壞例：「確保品質」。
   好例：「回報的每個 id 都必須真的存在於該 JSON 且無 card 鍵；數量與
   `jq '[.[] | select(.card == null)] | length'` 的結果一致」。
3. **回報格式**：明確欄位。例：「回報：①符合的 id 清單 ②總數 ③如有異常結構的題目，
   列出 id 與問題一行描述。不要貼題目全文」。

## 2. 回報合約（寫進每個派工 prompt 的固定尾段）

```
回報規則：
- 只回結論與必要證據，引用一律用 檔案路徑:行號，不要貼大段原文。
- 超過 30 行的產物（清單、報告、生成內容）寫到檔案，回報只給路徑＋5 行摘要。
- 遇到與任務描述矛盾的現實（檔案不存在、結構不同、指令失敗），停下回報現況，
  不要自行擴大解釋或繞路硬做。
- 明確標註：哪些是驗證過的事實、哪些是推測。
```

長產物落檔位置：臨時的放 scratchpad（系統提示有給路徑）；要跨 session 留存的放
`playbook/notes/`（自行建立）或任務相關目錄。

## 3. model 與 effort 顯式指定

Agent 工具有 `model` 參數（`haiku`/`sonnet`/`opus`）。不指定 = 繼承主對話模型。
**每次派工都顯式指定**，用這張表：

| 任務 | model | 理由 |
|---|---|---|
| 機械掃描、格式轉換、批次 rename、跑指令收輸出 | `haiku` | 便宜快，判斷需求低 |
| 一般搜尋、實作、資料修復、審查、驗收 | `sonnet` | 預設工作馬 |
| 難 bug 追蹤、架構設計、多方案取捨、對抗審查 | `opus` | 判斷密度高才值得 |

- 若 harness 提供 effort 參數（如 Workflow 的 `agent(prompt, {effort})`）：機械任務 `low`，
  預設 `medium`/繼承，驗收與審查 `high`。Agent 工具沒有 effort 參數就不用管。
- 模型名單會隨時間變。若表中名稱不可用，原則不變：**三檔制——便宜檔跑機械、
  中檔跑預設、最貴檔只給高判斷密度任務**，用當時可用的模型對號入座。

## 4. 驗證不自驗（最重要的一節）

寫的人不能當驗的人——同一個 context 會把自己的假設當事實。規則：

- **檔案產出** → 派 fresh `general-purpose`（sonnet）做 read-back：「讀 X 檔，回答
  ①是否存在且完整（不是空檔/半截）②是否滿足這些驗收條件（逐條列）③有無內部矛盾」。
  驗收 agent 的 prompt **不給實作過程**，只給驗收條件——避免它被實作者的思路帶著走。
- **程式碼改動** → 優先跑真驗證：`npm run build`（前端）、
  `verify_data_alignment.py`（資料）、實跑受影響指令。測試/build 通過 ≠ 完成，
  但不通過 = 一定沒完成。無法實跑的改動（如 CI 才會執行的 workflow）明說「未實跑」。
- **高風險判斷**（要刪東西、要花 API 錢、要改 SSOT、對外文案）→ 第二意見：
  再派一個 agent 只給結論不給推理過程，問「這個決定有什麼會出錯的方式」。
  兩個 agent 結論衝突 → 停下來問使用者。
- **內容品質**（出題、教材文字）→ 多答案評審：生成 2–3 版 → 派評審 agent 用明確
  rubric（正確性、與教材一致、無 AI 字眼、難度標註合理）選優，而非自己挑。

## 5. 升降級路徑

- **升級**（換更強模型重做）觸發條件，滿足任一：同一任務失敗 2 次且失敗原因不同；
  agent 回報自相矛盾；任務涉及不變量（CLAUDE.md 那 5 條）的解釋。
  升級時把兩次失敗的具體現象寫進新 prompt，不要只說「再試一次」。
- **降級**：發現任務其實是機械性的（例如「審查」變成「跑 lint」），改派 haiku 省成本。
- **放棄重拆**：升級後仍失敗 → 不是模型問題，是任務拆錯了。回 `02-judgment.md` §4
  檢查方向，重新拆解或問使用者。

## 6. 併發

互不依賴的派工在同一則訊息一起發（harness 支援並行）。有依賴就等前一個回報。
不確定有沒有依賴 → 當作有依賴，序列跑。並行 agent 不得寫同一個檔案。
