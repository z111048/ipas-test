# 03 — 派工 prompt 模板

用法：複製對應模板，填 `【】` 空格，整段作為 Agent 工具的 prompt。
每份模板已內建三件套（目標動機/驗收/回報）與回報合約，不要刪減這些段落。
model 選擇依 `01-dispatch.md` §3；下方標的是預設值。

共用尾段（每個模板結尾都要有，以下不重複列）：

```
回報規則：只回結論與必要證據，引用用 檔案路徑:行號；超過 30 行的產物寫檔並回報路徑＋摘要；
遇到與任務描述矛盾的現實就停下回報現況；標註哪些是驗證過的事實、哪些是推測。
```

---

## T1 搜尋／定位（subagent_type: Explore，model: haiku 或 sonnet）

```
任務：在 repo 中定位【要找的東西：符號/字串/設定/資料】。
動機：【為什麼要找，找到後要拿來做什麼——這決定你要回報到什麼精度】。
範圍：從【起點目錄/檔案類型】找起；已知線索：【關鍵字、命名慣例、相關 commit】。
注意：data/ 與 frontend/src/generated/ 下的 JSON 常達數百 KB，用 grep/jq 定位，不要整檔讀。
驗收條件：
- 每個結果給 檔案路徑:行號 ＋一行說明它是什麼
- 明確區分「確定是」與「可能相關」
- 若找不到，回報你搜過哪些 pattern 與目錄（讓我不用重搜）
回報格式：①確定命中清單 ②可能相關清單 ③搜尋覆蓋範圍一句話。
```

## T2 實作（subagent_type: general-purpose，model: sonnet）

```
任務：【要實作的功能/修復，一句話】。
動機與背景：【為什麼做、誰會用到、關聯的既有行為】。
規格：
- 【輸入/輸出/行為的具體描述】
- 遵守 CLAUDE.md 不變量（尤其：SSOT 不複製章節定義、前端文案無 AI 字眼）
- 風格與周邊程式碼一致（Python: 4-space/snake_case/Path；TS: 現有元件慣例）
改動範圍：預期動【檔案清單】；若發現需要動這清單以外的檔案，停下回報，不要擴大。
驗收條件（全部通過才算完成）：
- 【功能驗證：具體指令或操作＋預期結果】
- cd frontend && npm run build 零錯誤（若動了前端）
- python3 scripts/verify_data_alignment.py --level 【等級】 通過（若動了資料）
回報格式：①改了哪些檔（路徑:行號範圍）②驗收條件逐條的實際執行結果（貼指令輸出關鍵行）
③未盡事項或風險。
```

## T3 重構（subagent_type: general-purpose，model: sonnet；大範圍先派 Plan）

```
任務：重構【目標】，行為不得改變。
動機：【現在的痛點：重複/太長/耦合】。
不變式（重構的定義）：
- 對外行為、輸出檔案的內容與格式完全不變
- 【若有】既有輸出的 diff 驗證法：重構前先跑一次產出存到 scratchpad，重構後再跑，
  diff 兩者必須為空（或只有允許的差異：【說明】）
範圍：只動【檔案/模組】；發現需要動介面或其他呼叫端，停下回報。
驗收條件：
- 上述 diff 驗證通過，貼 diff 指令與結果
- build/verify 腳本通過（同 T2）
回報格式：①結構變化摘要（before/after 各 3 行）②diff 驗證結果 ③行為風險點。
```

## T4 研究／調查（subagent_type: general-purpose，model: sonnet；純 repo 內調查用 Explore）

```
問題：【要回答的具體問題，以問句寫出】。
動機：【這答案會決定什麼行動】。
來源優先序：①repo 內實際程式碼/資料（最權威）②官方文件 ③其他網路來源（需交叉驗證）。
驗收條件：
- 每個結論附來源（檔案:行號 或 URL）；網路來源至少兩個獨立出處才算「確認」
- 無法確認的部分明確標「未驗證」，不要用推測填補
- 回答直接針對問句，先給一句話答案再給依據
回報格式：①一句話答案 ②依據與來源 ③未驗證事項 ④（若適用）建議的下一步。
```

## T5 審查／驗收（subagent_type: general-purpose，model: sonnet；高風險用 opus）

> 給驗收 agent 的 prompt 只放驗收條件，**不要放實作過程或實作者的解釋**，避免帶偏。

```
任務：以全新視角審查【產出：檔案/diff/一批題目】。你沒有參與實作，不要信任任何未驗證的聲稱。
審查目標：【正確性 bug / 資料完整性 / 文案合規 / 與規格相符——挑選適用項】。
必查清單：
- 【逐條列出驗收條件，來自派工時的原始驗收條件】
- 檔案是否完整落地（非空檔、非半截、JSON 可被 jq 解析）
- 前端文案 grep 檢查 AI 字眼（規則見 playbook/02-judgment.md §5）（若適用）
- 規則之間有無互相矛盾、路徑/指令/參數是否真的存在（用 ls/grep 驗，不要目測）
判定標準：每個發現標 CONFIRMED(你實際驗證到) 或 PLAUSIBLE(懷疑但未能確認)，
附重現方式或反例。沒有發現就說沒有，不要為了交差硬找瑕疵。
回報格式：①判定：通過/不通過 ②發現清單（嚴重度排序，各附 檔案:行號＋一行修法）
③你實際執行過的驗證指令清單。
```

## 組合範例（實戰）

「修 mid_1151_s2 Q40 選項溢出」這類任務的標準流程：
1. T1（haiku）定位 Q40 在哪個 JSON 哪一行，回報結構。
2. 主對話決定修法（小 diff 自己修；大批同型問題套 T2 派工）。
3. `npm run build` ＋ dev server 實看該題。
4. T5（sonnet，fresh context）驗收：只給「Q40 選項 D 不得溢出、其他題不得受影響」
   的條件，不給修法過程。
