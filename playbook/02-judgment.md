# 02 — 判斷力外化（rubric 與 checklist）

這份檔把高階模型的直覺翻成可機械執行的判準。每條附正例／反例。
遇到 rubric 沒覆蓋的情況：套 §6 誠實條款，不要即興發揮。

## §1 何時該升級模型（或加派第二意見）

**升級判準**（滿足任一條）：
- [ ] 同一任務用不同方法失敗 ≥2 次
- [ ] 任務需要解釋或修改 CLAUDE.md 的 5 條不變量
- [ ] 錯了會造成不可逆損失（刪 gitignored 快取、覆蓋人工策展 JSON、對外部署）
- [ ] 兩個資訊來源矛盾且無法用指令驗證哪個對

**正例**：修 `export_guide_outline_data.py` 的 heading 層級判斷邏輯——PDF x 座標相同、
無明確規則可依，錯了會汙染全部章節資料 → 值得 opus ＋第二意見。
**反例**：改 20 個檔案裡的字串「Codex 100 題」→「精選 100 題」——量大但機械，
失敗會被 build 抓到 → haiku/sonnet 即可，升級是浪費。

## §2 何時算真的完成（Definition of Done）

宣告完成前逐項打勾：
- [ ] 使用者**原話要求**的每一點都有對應產出（回頭重讀原始訊息，不是讀自己的摘要）
- [ ] 跑過本 repo 的兩道防線：前端動過 → `npm run build` 零 TS 錯誤；
      資料動過 → `verify_data_alignment.py` 通過
- [ ] 產出被 fresh agent read-back 驗過（規則見 `01-dispatch.md` §4）
- [ ] 破壞性腳本的後置動作做完（s1c4 補回、`git status` 確認中級檔案還在）
- [ ] 對使用者的回報寫的是「實際發生的事」不是「預期發生的事」（測試失敗就寫失敗）

**正例**：修了 Q40 選項溢出 → 改 JSON → build 通過 → dev server 截圖確認該題渲染正常
→ 回報附題目 id 與確認方式。這是完成。
**反例**：改了 JSON、build 通過，回報「已修復」——但沒看過該題實際渲染。
build 只驗型別，不驗內容正確性。這不是完成，是「大概完成」，要明說驗到哪一層。

## §3 何時該停下來問使用者

**必問**（不問就做 = 越權）：
- [ ] 要刪除或覆蓋「不是這個 session 建立的」檔案，且它不在 build artifacts 清單
- [ ] 要動人工策展資料（`subject{N}_questions.json` 的既有題目、手動修正過的內容）
- [ ] 要花超過小額的 API 費用（全量 vision 重跑、大批出題）
- [ ] 使用者要求與不變量衝突（例如要在前端文案寫「AI 生成」）
- [ ] 兩個合理方案的取捨取決於使用者沒說的偏好（例如：出題要偏難還是偏易）

**不問**（自己決定並在回報中說明理由）：可逆的實作細節、命名、檔案組織、
用哪支既有腳本、先做哪個子任務。

**正例**：發現 `exam_pages_cache/` 未列入 .gitignore（git status 顯示 untracked）——
提交它？加進 .gitignore？這改變 repo 政策 → 問。
**反例**：「修這題的選項 D」但發現選項 C 也有同樣問題——順手一起修並回報，不用問。
同一症狀的鄰近實例屬於原任務範圍。

## §4 方向錯了的訊號（換路，不要重試）

重試（同方法再來一次）只在「隨機性失敗」時有效：網路逾時、API 限流、race condition。
以下訊號出現時，**重試是浪費，要換路**：

- 連續 2 次修正都產生新的、不同位置的錯誤 → 你在打補丁不在治病，回頭找根因
- 為了讓方案成立，需要的「特例處理」超過 3 個 → 抽象選錯了，換方案
- 開始想「繞過」驗證（跳過 build、註解掉檢查、放寬驗收）→ 停，這是方向錯誤的最強訊號
- 任務越做越大（原本改 1 檔，現在要動 6 檔）→ 停下來回報 scope 變化，讓使用者決定
- 對同一份資料的理解被推翻 2 次（「原來這欄位是那個意思」）→ 先派 Explore 把資料
  結構弄清楚再動手

**正例**：parse 考題 PDF 一直漏題，試了 3 種 regex 都各漏不同題 → 換路：這批 PDF
是圖片型，該走 `gemini_exam_vision_extract.py` 而不是繼續調 regex。
**反例**：Vision API 回 429 → 這是限流，等 30 秒重試即可，不需要換架構。

## §5 品質底線怎麼驗（本 repo 專屬）

- **教材內容**：與 PDF 原頁比對（`frontend/public/guide-pages/` 有截圖）。抽驗法：
  每章隨機抽 2 個 heading，確認在原 PDF 同頁存在且層級一致。
- **題目**：①答案可從教材推出（引用章節）②四個選項互斥且唯一正解 ③`card.confusion`
  真的是易混淆點不是空話 ④無 AI 工具字眼。抽驗 10% 或至少 5 題。
- **前端文案**：grep 檢查 `grep -rn "AI 生成\|Codex\|LLM\|Gemini\|Claude" frontend/src/`
  ——出現在使用者可見字串就是違規（變數名/註解/import 不算；「AI 應用規劃師」「生成式 AI」豁免）。
- **資料完整性**：改題目 JSON 後 `jq` 驗 schema 必要欄位都在、`answer` ∈ {A,B,C,D}、
  `options` 恰四鍵。

## §6 誠實條款：harness 補不了的事

拆解、驗證、多樣本評審能把**執行品質**補到接近高階模型；以下補不了，遇到就照寫的做：

1. **模糊需求的解讀**（使用者一句話有 3 種合理讀法）→ 不要挑一種默默做。
   列出讀法、選一個最可能的說明理由、做可逆的最小版本、回報時明示假設。
   影響大且不可逆 → 直接問（§3）。
2. **品味判斷**（文案語感、UI 美感、題目「好不好」的最後 10%）→ 多答案評審選優
   只能到「不差」，到不了「好」。做法：產出 2–3 版讓使用者挑，明說「此類判斷
   建議人工定奪」，不要假裝有把握。
3. **領域正確性**（AI 考試的專業內容對錯）→ 模型可能一本正經地錯。教材相關的
   事實爭議一律回到 PDF 原文為準；PDF 沒寫的不要自行補充進教材。
4. **查不到的事** → 標註「未驗證」，不要編。寫進產出的每個檔名、指令、參數
   都要實際確認存在（用 ls/grep，5 秒的事）。
