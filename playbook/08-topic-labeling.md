# 08 — 考古題熱度、概念標籤與心智圖

**狀態：章節熱度圖已上線（`/mindmap`）；概念詞彙表已定案 174 個概念
（`data/topics/topics.json`，`signed-off`），但**尚未拿去標任何題目**（§7-2）；
出題配額已改為熱度加權（§7-4）。**

## §1 這條線在做什麼

出題原本是「每個小節平均出 2 題」，跟實際考試分布無關。這條線反過來：
**先量出考古題實際考哪裡，再用熱度驅動出題配額與站上導覽。**

三個資料軸，彼此正交，不要混在一起：

| 軸 | 回答什麼 | 現況 |
|---|---|---|
| **位置**（章節樹） | 這題考講義哪一段 | ✅ 已有，`guideExamAnnotations` |
| **概念**（受控詞彙） | 這題考什麼觀念 | ⚠️ 詞彙表已定案 174 個，未指派到題目 |
| **熱度**（統計） | 哪裡考得多 | ✅ 章層級已上線，標題層待定 |

位置軸是樹狀的，概念軸是跨章節的圖——**硬把概念塞進樹只會讓樹變成圖**。

## §3 章節熱度圖（已上線）

```bash
python3 scripts/export_guide_mindmap.py [--check]   # → guideMindmap/{subjectId}.json
```

只讀既有 committed 產物，無 API 花費，可隨時重跑。前端 `/mindmap`。

三個設計決定，改動前先讀：

- **各章題數不可相加**。一題通常引用數章，逐章加總 905 但實際只有 450 題。
  子樹彙總取 **max** 不是 sum，頁面也明講這件事——不然使用者會自己加起來。
- **同時給密度（每千字題數）**。章節篇幅差一個數量級（最長三萬多字），
  只看題數會把「長」讀成「熱」。兩種排序的名次確實不同。
- **標註只到章層級，節點以空心表示「尚無統計」而不是 0**。假的深度比沒有深度糟。

熱度分布（前四）：初級科目二「生成式AI 導入評估規劃」127 題、初級科目一
「機器學習概念」114 題、中級科目三「機器學習建模與參數調校」23 題、
中級科目二「數據處理技術與工具」16 題。**初級的集中度遠高於中級。**

## §4 標題層熱度：技術可行，但價值有限

量過了（2026-08-08）：

- 96.4% 的題目落得到標題節點，360 個標題節點有命中，中位距離 4 個區塊。
- 但**標題名稱空泛**：最熱的是「C. 挑戰與未來方向」（69 題）。

一度以為是映射把不相關內容堆在一起，查證後**不是**：那段 370 字裡有資料品質、
可解釋性、透明性、公平性、去偏、跨領域整合，是名副其實的高產段落，只是標題取得很空。

> 結論：位置軸再往下挖也回答不了「該準備哪個觀念」。要往下做應該做概念軸，
> 不是把樹挖深。標題層資料本身可用，若要上線，節點標籤得換成概念而非原標題。

## §5 概念詞彙表（已定案，`data/topics/topics.json`）

```bash
python3 scripts/build_topic_vocabulary.py                 # 分科目收斂 → 草稿
python3 scripts/build_topic_vocabulary.py --consolidate    # 合併大類與重複概念
python3 scripts/build_topic_vocabulary.py --show           # 依大類印出
python3 scripts/build_topic_vocabulary.py --dedupe-pairs    # 語意去重 → 合併配對清單（待人工勾選）
python3 scripts/build_topic_vocabulary.py --apply-pairs     # 套用勾選結果 → topics.json（定案版）
```

三個檔各有角色，不要混：`topics_draft.json`（草稿，不動）→ `merge_pairs.json`
（合併決定，含 `stillOpen` 未決項）→ `topics.json`（定案版，標題目時用這個）。

`key_concepts` 不能直接當標籤：3,018 個詞組裡 **87% 只出現一次**，
純字串正規化（NFKC、去括號英文、去冒號後解釋）只能把 2,678 個相異值降到 2,607。
收斂是語意工作，所以分科目請模型收斂，再合併統整成 **204 概念 / 8 大類**。

**2026-08-08 定案：204 → 174**（併掉 30 個）。`known_duplicate_pairs.json` 是先寫好的
人工基線，用途是**驗收去重輸出**：漏太多代表太保守，基線外的新配對要逐條看，
其中 5 組 `keepSeparate`（`異常偵測` vs `異常值偵測`、四個多模態概念、
`模型優化` vs `效能優化`）**看起來像重複但不是**，被合併就是誤殺——實測全部存活。

先寫基線再跑模型這件事本身就有回報：第一次去重只挖到 10 組，是基線讓「模型太保守」
變成一個數字而不是感覺。

`stillOpen` 有 5 組未決（`模型評估`/`評估指標`、`機率分佈`/`機率與統計`、
`特徵縮放`/`資料標準化`、`異常值偵測`/`離群值處理`、兩個 AI 幻覺概念），
要動之前先看標註分布。

## §6 這條線踩過的坑（全是「看起來成功、實際上錯」）

> 教訓 2026-08-08：整頁 PDF 渲染送給視覺驗證器等於洩題。根因：公告試題 PDF 的答案
> 印在題目表格最左欄。規則：只送 `image_*.png` 圖形裁圖，排除 `page.png`/`table_*.png`；
> 沒有裁圖的題直接跳過。偵測手段見 `07` 的 `answer_echo_rate`。

> 教訓 2026-08-08：7 個分組壞了 4 組，程式照樣合併剩下 3 組寫檔並印出「成功」。
> 根因：分組失敗只回空陣列，沒有任何地方檢查完整性。規則：批次彙總一律「任一分組
> 失敗就拒絕寫出」，不要產出看起來完整的部分結果。

> 教訓 2026-08-08：拿模型生成的 alias 當合併鍵，等於對「共用任一別名」取傳遞閉包，
> 一條爛連結讓「欠擬合」吞掉 133 個別名（含特徵工程、資料標準化）。
> 根因：alias 是自由文字、品質不受控。規則：合併鍵只用正式名稱，別名只做累積；
> **每一次合併都印出 `合併「X」→「Y」`**，讓誤殺變成可掃視的清單。

> 教訓 2026-08-08：字串包含關係把「非監督式學習」併進「監督式學習」（意思相反）。
> 根因：中文的非/半/自/反/無/未/不/逆 前綴會翻轉語意。規則：名稱包含式合併要擋
> `MEANING_CHANGING_PREFIX`；寧可少併（人工再併），不要靜靜產生事實錯誤。

> 教訓 2026-08-08：統整跑在已統整的輸出上，重跑會累積合併。規則：彙總步驟一律從
> 原始草稿重算（原始草稿另存 `_drafts_by_subject.json`），保持可重入。

> 教訓 2026-08-08：「回應為空」與「回應被截斷」都報成「無結果」，於是重試三次都白費
> ——真因是 `max_tokens` 太小，重試不可能成功。規則：錯誤訊息要能區分這兩者
> （`空回應` vs `回應無法解析（N 字，可能被截斷）`）。

> 教訓 2026-08-08：大類歸併是 LLM 呼叫，每次重跑得到 7 或 8 個不同分類。
> 規則：把歸併結果存進 `parentMap` 沿用，要重算才加 `--remap`。
> 凡是 LLM 產生的「結構」都要存下來，不然資料每次自我重組。

**貫穿這些坑的一條**：有效的防護都不是更強的模型，而是**讓錯誤現形的機制**——
選項亂序把洩題變成錯誤率、`answer_echo_rate` 把偷看變成數字、逐條列印合併記錄把
誤殺變成清單。設計彙總步驟時先問：**這一步錯了，會不會有人看得出來？**

## §6a 審核機制（2026-08-08 建立）

```bash
python3 scripts/audit_resources.py            # Layer 1 確定性；build_web.py 會先跑，FAIL 中止 build
python3 scripts/review_committed_notebooks.py --python <有 pandas/sklearn 的直譯器>
```

三層：**Layer 1** 確定性（不需模型金鑰，`audit_resources.py`）→ **Layer 2** 語意
（`verify_question_answers.py` 多模型共識、notebook 語意複查）→ **Layer 3** 人工佇列。
例外一律寫 `data/audit_allowlist.json` **並附理由**，目前 1 筆。

> 教訓 2026-08-08：語意審核器不是確定性的——同一份 notebook 連跑三次，每次照出的
> 低嚴重度項目都不一樣。根因：模型判斷本來就有變異。規則：**別把「這輪 0 筆」當成
> 「這本乾淨」**；收工條件是「照出來的每一筆都逐條看過並處置」，不是跑到全綠為止。
> 另外自己補的說明也要先讀那格程式碼再寫（我就寫錯過一格，下一輪被抓出來）。

> 教訓 2026-08-08：閘門若會誤報就會被繞過。第一版審核器誤判 483 筆中英夾雜
> （把「Transformer 架構」當夾雜）、62 筆詞彙表（欄位假設錯）、27 筆 notebook
> （拿草稿審核當現況）。規則：**寫閘門的力氣要有一半花在驗證閘門本身**，
> 上線前先確認它對已知正確的資料回報乾淨、對已知錯誤的資料抓得到。
