# 前端體驗與載入效能：第一輪（2026-11-11）

目標：用最少的修改，讓新訪客更快看到畫面、分享連結時有預覽圖、付費使用者最常用的學習指引頁載入更輕、
頁面不再跳動。本文件同時是**規劃**與**調整紀錄**；每一項都對應到量測到的問題，不做沒有數據支持的改動。

## 1. 基準量測（改動前，正式站 `ipas-test.onrender.com`，commit 14674b1）

量測方式：Playwright Chromium。桌機 1440×900 不限速；手機 390×844，網路限 1.6 Mbps／延遲 150 ms、CPU 降速 4 倍。
腳本不進 repo（一次性量測），指標定義：FCP＝第一次出現內容、LCP＝最大內容出現、CLS＝版面位移累計（>0.25 屬於差）。

| 頁面 | 裝置 | FCP | LCP | CLS | 傳輸量 |
|---|---|---|---|---|---|
| 首頁 | 桌機 | 284 ms | 588 ms | 0.020 | 1,059 KB |
| 學習指引 s1c1 | 桌機 | 188 ms | 1,008 ms | **0.275** | 3,169 KB |
| 公告試題 jr_1151_s1 | 桌機 | 180 ms | 656 ms | 0.140 | 1,219 KB |
| 首頁 | 手機 | 1,812 ms | 2,120 ms | 0.001 | 357 KB |
| 學習指引 s1c1 | 手機 | 1,796 ms | 內文約 10 秒才出現 | **0.279** | — |
| 公告試題 jr_1151_s1 | 手機 | 1,820 ms | 4,020 ms | **1.497** | 377 KB |

找到的問題（依效益排序）：

1. **Google Fonts 的 CSS 有 136 KB，而且會擋住畫面**。`wght@400;500;700;900` 讓 Google 回傳 432 條 `@font-face`
   （108 個字元分片 × 4 個字重，未壓縮 500 KB），比整個 JS 進入點（100 KB）還大。四個字重其實指向同一批可變字型檔，
   改用 `wght@400..900` 只會回傳 108 條（35 KB），字型檔完全相同。
2. **學習指引頁的程式有 1,023 KB（壓縮後 222 KB）**，其中大半是 `react-syntax-highlighter` 的完整 Prism（371 種語言），
   實際只用到 Python，而且只有含實作練習的章節才用得到。
3. **頁尾在載入時跳動**：頁尾在路由的 Suspense 外面，內容還沒到時先貼在畫面上方，內容到了又被推走。
   手機公告試題頁 CLS 1.497 幾乎全部來自這裡。
4. **學習指引內文載入時版面被撐開**：內文區塊從 50 px 長到 397 px，把下方的上一章／下一章導覽推走（CLS 0.24）。
5. **分享連結沒有預覽圖**：沒有 `og:image`、`og:url`、`twitter:card`，貼到 LINE、Threads、Facebook 只有文字。
   `theme-color` 還是改版前的深藍 `#17324d`。
6. **`index.html` 的 `<div id="root">` 是空的**：JS 與 CSS 到之前整頁空白。
7. **Render 的快取標頭是 `max-age=0`**：連檔名帶雜湊的 JS／CSS 與圖片，每次回訪都要重新向伺服器確認。
8. React 與應用程式碼打在同一個進入點，每次部署回訪者都要重抓整包。
9. 首頁對回訪者沒有「接續上次」的入口，每次都要從側欄重新找章節。

## 2. 規劃（四個工作包）

| 編號 | 調整 | 預期效益 | 動到的檔案 |
|---|---|---|---|
| P1-1 | 字型改可變字重 `400..900`，CSS 改成不擋畫面的載入方式 | 首屏少 100 KB、少一個阻塞請求 | `frontend/index.html` |
| P1-2 | `index.html` 內嵌首屏外殼（頁首、站名、說明文字） | HTML 一到就有畫面；不跑 JS 的爬蟲也讀得到站名與說明 | `frontend/index.html` |

| P3-1 | 實作練習區塊改用 PrismLight（只註冊 Python）並延後載入 | 學習指引頁程式少約 600 KB | `ColabSection.tsx`、`GuidePage.tsx` |
| P3-2 | 學習指引內文載入期間保留高度 | 學習指引頁 CLS 降到 0.1 以下 | `GuidePage.tsx` |

| P4-2 | 首頁加「繼續上次進度」 | 回訪者一鍵回到上次的章節或試卷 | `App.tsx`、`HomePage.tsx`、新增 `utils/lastVisit.ts` |
| P4-3 | 滑鼠移到或手指按下連結時先載入該頁程式 | 點進學習指引、試題、練習時少等一段 | `App.tsx`（或新增小工具） |
| P4-4 | 標題斷行平衡、換頁淡入 | 手機標題不再剩一個字獨立一行 | `index.css` |

### 評估後這一輪不做

- **HashRouter 改 BrowserRouter**（讓每個章節有獨立網址可被搜尋引擎收錄）：效益最大但要動兩個站的 404 回退、
  所有既有連結與 E2E 測試，不符合「最小修改」，另案評估。
- **`guideImages.json`（877 KB）與 `guideHierarchy.json`（340 KB）拆成每章一檔**：要改資料 pipeline 與對齊測試，列為下一輪第一候選。
- **改用系統字型**：可再省約 780 KB 字型檔，但 Windows 上的字體外觀會變，屬於視覺決定，不在這輪擅自更動。
- **Service Worker／離線快取**：有付費使用者，快取失效出錯的代價高。
- KaTeX CSS 移出進入點：只省約 5 KB，不值得動四個檔。
- `robots.txt`／`sitemap.xml`：單頁 hash 路由只有一個網址，沒有實質效果。

## 3. 需要使用者在 Render 後台操作（程式改不到）

Render 靜態站 → Settings → Headers，加入：

| Path | Header | Value |
|---|---|---|
| `/assets/*` | `Cache-Control` | `public, max-age=31536000, immutable` |
| `/images/*` | `Cache-Control` | `public, max-age=86400` |
| `/pdf-assets/*` | `Cache-Control` | `public, max-age=86400` |

`/assets/*` 的檔名帶內容雜湊，內容變了檔名就變，可以永久快取。`index.html` 維持現在的 `max-age=0`，
這樣部署後使用者立刻拿到新版。GitHub Pages 的快取固定 10 分鐘，無法調整。

## 4. 調整紀錄

狀態：2026-11-11 實作與本機驗收完成，**尚未 commit、尚未部署**。實作由三個 Sonnet 代理分包進行，
另一個沒看過實作過程的 Sonnet 代理審查整份 diff；主對話負責整合、量測與修正。

### 4.1 前後數據

量測方式：同一台機器、同一份資料，分別建置 commit 14674b1（改動前）與工作樹（改動後），用 `vite preview` 服務，
Playwright Chromium 每格跑三次取中位數。桌機 1440×900、10 Mbps／延遲 40 ms；手機 390×844、1.6 Mbps／延遲 150 ms、CPU 降速 4 倍。
「內容出現」＝真正的頁面內容（不是外殼）出現在畫面上的時間。量測腳本是一次性的，不進 repo。

| 裝置 | 頁面 | 第一次出現畫面（FCP） | 內容出現 | 版面位移（CLS） | 傳輸量 |
|---|---|---|---|---|---|
| 桌機 | 首頁 | 360 → **208 ms** | 664 → **584 ms** | 0.020 → 0.010 | 1,066 → 968 KB |
| 桌機 | 學習指引 s1c1 | 364 → **208 ms** | 1,468 → **1,155 ms** | 0.275 → **0.028** | 3,190 → 2,882 KB |
| 桌機 | 公告試題 jr_1151_s1 | 372 → **204 ms** | 850 → **733 ms** | 0.140 → **0.000** | 1,227 → 1,129 KB |
| 手機 | 首頁 | 1,832 → **1,012 ms** | 2,127 → **1,610 ms** | 0.001 → 0.001 | 1,066 → 968 KB |
| 手機 | 學習指引 s1c1 | 1,816 → **988 ms** | 8,770 → **6,897 ms** | 0.275 → **0.023** | 2,904 → 2,883 KB |
| 手機 | 公告試題 jr_1151_s1 | 1,820 → **1,012 ms** | 3,556 → **3,063 ms** | 1.400 → **0.006** | 1,289 → 1,190 KB |

程式與樣式大小：

| 項目 | 改動前 | 改動後 |
|---|---|---|
| 字型 CSS（傳輸） | 135.6 KB，擋畫面 | 34.4 KB，不擋畫面 |
| 進入點 JS（原始／gzip） | 333 KB／101 KB，一個檔 | 應用程式 117 KB／32 KB＋框架 218 KB／69 KB（框架檔在部署之間不變） |
| 學習指引頁 JS（原始／gzip） | 1,023 KB／284 KB | 390 KB／64 KB；實作練習另拆 41 KB／12 KB，只有含實作練習的章節才載入 |

讀表時要注意的三點：

- 改動後首頁與試題頁的 LCP 等於 FCP（外殼的標題被算成最大內容），所以這裡用「內容出現」當作真正的指標，不拿 LCP 邀功。
- 手機學習指引頁的 LCP 仍在 14 秒上下（14,968 → 14,348 ms），最大內容是章節首圖，瓶頸是 877 KB 的 `guideImages.json`
  與每章 300 KB 上下的內文檔，這一輪沒有處理，見 4.4。
- 腳本直接改網址切到下一章時量到的位移（桌機 0.81 → 0.51、手機 0.52 → 0.11）主要發生在切換後 24 ms，來源是兩章頁首內容不同
  （s1c1 有提示框、s1c2 沒有）。真人點擊後 500 ms 內的位移不計入 CLS，所以這個數字是量測方式造成的，不是使用者感受到的跳動。

### 4.2 各項實際做法

| 編號 | 實際做法 | 檔案 |
|---|---|---|
| P1-1 | 字型網址改成 `wght@400..900`；用 `preload as=style`＋`media="print" onload` 載入，另附 `<noscript>` 後備。站內用到的字重（500／600／700／800／900）都在範圍內 | `frontend/index.html` |
| P1-2 | `#root` 內放靜態外殼（頁首、站名、一句說明、「載入中…」），約 1 KB 內嵌樣式；React 掛載時自動取代。另加停用 JavaScript 時的提示。**外殼刻意用系統字型**，原因見 4.3 | `frontend/index.html` |
| P1-3 | `manualChunks` 只把 react、react-dom、scheduler、react-router 拆成 `vendor` | `frontend/vite.config.ts` |

| P4-1 | 路由內容包進 `.route-view`，一般頁至少撐滿可視高度，頁尾固定在第一屏下方；學習指引路由用 `display: contents` 不影響原版面 | `App.tsx` |

### 4.3 驗收過程中發現並修正的問題

1. **外殼讓手機上真正的內容變慢**。第一版外殼用 Noto Sans TC，瀏覽器在程式還沒載完時就開始抓字型檔，
   在 1.6 Mbps 下和首頁程式搶頻寬：FCP 快了 0.8 秒，但首頁內容出現反而從 2,127 ms 變成 2,534 ms。
   改成外殼用系統字型後，字型檔等真正的頁面出來才抓，內容出現時間降到 1,610 ms。
2. **實作練習延後載入失敗會拖垮整頁**（審查發現）。剛部署完的舊分頁抓不到那段程式時，整個學習指引頁會變成錯誤畫面。
   改成載入失敗只隱藏實作練習區塊。實測擋掉該檔後內文與導覽照常顯示。
3. **內文載入失敗時桌機的上一章／下一章消失**（審查發現）。條件改成內文就緒或載入失敗都顯示。
4. **首頁大標在手機斷成「應用規／劃師」**。`text-wrap: balance` 造成的；首頁標題改成兩個不可拆的片語，
   手機顯示為「iPAS AI 應用規劃師／備考平台」。
5. 頁尾包裝層第一版漏了 `shrink-0`，頁尾會蓋住內容，實作階段已修正。

驗收結果：`uv run python tests/run_all.py` 21/21 通過（281 秒）；`npm run build` 零 TS 錯誤。
另外實測：三種路徑的「繼續上次進度」名稱正確（學習指引・人工智慧概念、章節練習・資料處理與分析概念、公告試題全名）；
`mid-s1c1` 的實作練習展開後 6 段程式都有語法上色；每頁只有一個 `<h1>`。

`tsconfig.node.json` 單獨跑 `tsc` 會報錯（專案沒裝 `@types/node`），這在改動前就存在，也不在 `npm run build` 的檢查範圍內，這一輪沒動。

### 4.4 留給下一輪

- **學習指引頁的資料量**：手機內文仍要約 7 秒才出現。`guideImages.json`（877 KB）拆成每章一檔是最有效的下一步，要改資料 pipeline 與對齊測試。
- **內文圖片沒有寬高資料**：圖片載入時仍會撐開版面。要在 pipeline 輸出寬高欄位，前端才能預留空間。
- 第 3 節的 Render 快取標頭仍待在後台設定；設定後回訪者不必每次重新確認程式檔與圖片。
