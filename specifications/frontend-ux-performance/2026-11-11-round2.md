# 前端體驗與載入效能：第二輪（2026-11-11）

第一輪（`2026-11-11-round1.md`，commit 30ec7c4）留下的最大問題是：慢速手機網路第一次打開學習指引時，內文要 8 秒才出現。
這一輪只處理這一件事，連帶把概念圖卡撐開版面的問題一起解掉。

狀態：實作與本機驗收完成，提交在分支 `perf/frontend-round1`，**尚未 push、尚未部署**。

## 1. 原因

手機條件（390×844、1.6 Mbps／延遲 150 ms、CPU 降速 4 倍）第一次造訪 `#/guide/s1/s1c1` 的請求順序：

| 時間 | 發生的事 |
|---|---|
| 0–1.2 秒 | HTML、進入點程式、框架、樣式 |
| 1.2–6.8 秒 | 學習指引頁的程式（約 335 KB，含 125 KB 的整站圖卡清單），**同時**有 25 個字型檔（約 1.4 MB）在搶頻寬 |
| 6.9–8.0 秒 | 頁面程式執行完，才開始請求這一章的內文檔 |
| 8.2 秒 | 內文出現 |

三個原因疊在一起：

1. **字型搶頻寬**。頁首一渲染出來就用到 Noto Sans TC，瀏覽器立刻開始抓字型檔。擋掉字型做對照實驗，內文出現時間從 8.2 秒變成 3.8 秒。
2. **整站圖卡清單擋在前面**。`guideImages.json` 有 727 張圖卡的資料，學習指引頁每次只用其中一章，卻要整份下載完才能渲染。
3. **串接下載**。這一章的內文檔要等頁面程式下載、執行完才開始請求，中間白等。

## 2. 做法

| 編號 | 做法 | 檔案 |
|---|---|---|
| R2-1 | **字型延後啟用**。字型樣式表維持 `media="print"`（不擋畫面、不啟用字型），第一次造訪時等路由頁渲染出來才切成 `all`（`App.tsx` 的 `WebFontGate` 與路由頁放在同一個 `Suspense` 內，路由頁載完才會掛載）。啟用後在 `localStorage` 記下 `ipas:webfont=1`；回訪者由 `index.html` 內嵌的一小段程式在樣式表載完時直接啟用，行為和改動前相同，不會每次都閃一下字型。拿掉字型 CSS 的 `preload`。`<noscript>` 後備保留 | `frontend/index.html`、`frontend/src/App.tsx`、新增 `frontend/src/utils/webFont.ts` |
| R2-2 | **圖卡清單每章一檔**。`export_guide_images_data.py` 在原本的 `guideImages.json` 之外，另外輸出 `frontend/src/generated/guideImagesByChapter/{guideKey}/{nodeId}.json`（41 檔，每檔 0.4–19 KB）。學習指引頁只載入當前章節那一檔，並和內文一起到位（同一個 `Promise.all`），避免圖卡晚到把內文往下推。清單缺檔或載入失敗時當成沒有圖卡，內文照常顯示。`guideImages.json` 內容不變，概念圖卡頁與稽核腳本照舊使用 | `scripts/export_guide_images_data.py`、新增 `frontend/src/generated/guideImagesByChapter/`、`frontend/src/pages/GuidePage.tsx` |
| R2-3 | **章節資料和頁面程式同時下載**。把兩個章節資料的動態 import 表搬到小模組，網址一確定是某一章（直接開該章，或點下章節連結的那一刻）就開始抓該章的內文檔與圖卡清單；學習指引頁之後呼叫同一個 import，拿到的是同一份，不會重複請求。用檔名比對，沒有硬編章節清單 | 新增 `frontend/src/utils/guideChapterModules.ts`、`frontend/src/utils/routePrefetch.ts`、`GuidePage.tsx` |
| R2-4 | **圖卡預留空間**。727 張概念圖卡全部是 1792×1024，`<img>` 加上 `width`／`height` 與 `h-auto`，圖片還沒載入就先佔好位置。PDF 原圖尺寸不一，這一輪沒動 | `GuidePage.tsx` |
| R2-5 | 一致性檢查：每章檔的集合與內容必須和 `guideImages.json` 的 `byChapter` 完全相同。加在既有測試檔內，驗收項目數仍是 21 | `tests/test_pipeline_output_safety.py` |

`playbook/pipeline-script-catalog.md` 已補上腳本的新輸出。

## 3. 前後數據

量測方式和第一輪相同：同一台機器分別建置 commit 30ec7c4（改動前）與工作樹（改動後），`vite preview` 服務，Playwright Chromium 每格三次取中位數，每次都是全新的瀏覽器狀態（等同第一次造訪）。
「內容出現」的定義：首頁是科目選擇區出現；學習指引是**章節內文**渲染出來（超過 5 個內文區塊）；公告試題是題目區出現。

| 裝置 | 頁面 | 內容出現 | 版面位移（CLS） | 傳輸量 |
|---|---|---|---|---|
| 手機 | 學習指引 s1c1 | 8,230 → **3,174 ms** | 0.023 → **0.000** | 2,597 → 2,528 KB |
| 手機 | 公告試題 jr_1151_s1 | 3,078 → **2,652 ms** | 0.006 → 0.007 | 1,190 → 1,193 KB |
| 手機 | 首頁 | 1,606 → 1,650 ms | 0.001 → 0.001 | 968 → 970 KB |
| 桌機 | 學習指引 s1c1 | 1,374 → **618 ms** | 0.028 → **0.000** | 2,882 → 2,696 KB |
| 桌機 | 公告試題 jr_1151_s1 | 723 → **624 ms** | 0.000 → 0.001 | 1,129 → 1,131 KB |
| 桌機 | 首頁 | 584 → 582 ms | 0.010 → 0.010 | 968 → 970 KB |

第一次出現畫面（FCP）沒有變化（手機約 1.0 秒、桌機約 0.2 秒）。首頁的差距在量測誤差內。

程式大小：

| 項目 | 改動前 | 改動後 |
|---|---|---|
| 學習指引頁必須先下載的共用程式 | 877 KB／gzip 125 KB（整站圖卡清單＋HTML 解析器包在同一個檔） | 169 KB／gzip 52 KB（只剩 HTML 解析器）＋當前章節的圖卡清單 0.4–19 KB |
| 概念圖卡頁 | 20 KB＋上面那個 877 KB 共用檔 | 374 KB／gzip 44 KB＋169 KB 共用檔 |
| 進入點程式 | 117 KB／gzip 32.4 KB | 128 KB／gzip 34.3 KB |

讀表時要注意：

- **代價一：第一次造訪時，字型比較晚換上**。文字先用系統字型顯示，再換成 Noto Sans TC。首頁第一個字型檔載完的時間，手機從 2.07 秒變成 2.43 秒，桌機從 0.59 秒變成 0.75 秒。回訪者不受影響。換字型時量到的版面位移都在 0.01 以下。
- **代價二：進入點程式多了 2 KB（gzip）**，因為章節資料的對照表搬到進入點才能提早下載。附帶影響是章節內文重新發佈時，進入點的檔名雜湊也會變，回訪者要重抓這個約 35 KB 的檔（以前變的是學習指引頁那個檔）。
- **手機學習指引頁的 LCP 仍在 12.8 秒**（13,164 → 12,768 ms）。最大內容是章節第一張概念圖卡（127 KB），它和 1.4 MB 的字型檔同時下載。這一輪沒有解決，見第 6 節。
- 表中數字是審查修正前量的；修正只改變「從別頁點進章節」的時機，直接開章節的路徑沒變，修正後單次複測手機學習指引內文為 3,186 ms。
- 1.6 Mbps 是 Lighthouse 的慢速行動網路標準條件。台灣一般行動網路快得多，實際受益最明顯的是訊號差或第一次造訪的使用者。

## 4. 更正第一輪的數字

第一輪 4.1 表格中學習指引頁的「內容出現」（手機 8,770 → 6,897 ms、桌機 1,468 → 1,155 ms）量到的其實是**頁面框架與章節大綱**出現的時間，不是內文。
量測腳本當時用「畫面上出現章節標題文字」判斷，大綱裡也有同樣的文字。第一輪做完後，內文實際出現時間是手機 8,230 ms、桌機 1,374 ms（本文件的改動前數字）。
第一輪其他頁面與其他欄位的數字不受影響。第一輪改動前（14674b1）的內文時間沒有用正確條件量過。

## 5. 驗收

- `uv run python tests/run_all.py`：21/21 通過。`npm run build` 零 TS 錯誤。`verify_data_alignment.py` 初級、中級都通過。
- 重跑 `export_guide_images_data.py` 輸出到暫存路徑，`guideImages.json` 與現有檔逐位元相同，41 個每章檔也相同；`guideContent/` 沒有任何變動。
- 另一個沒看過實作過程的 Sonnet 代理依 17 條驗收條件審查並實測：16 條通過、1 條不通過（已修正，見下）。實測範圍包含：第一次造訪四種路由的字型請求都晚於路由頁程式載完；回訪時字型不延後；停用 JavaScript、`localStorage` 丟例外、字型網域連不上三種情況頁面都正常；三章的圖卡數量、順序與改動前相同；圖卡清單載入失敗時內文照常；圖片未載入時已預留高度；省流量模式不做推測性下載；異常章節代號不會抓到不相干的檔。

### 審查發現並修正的問題

1. **預先載入失敗後，該章永遠載不進來**（必修，已修）。第一版在滑鼠移上或手指按下章節連結時就預先抓章節資料。Chromium 會記住失敗的動態 import，同一個檔在整頁重新載入前不會再請求；如果預先抓的那一刻剛好斷線，之後網路恢復再點進該章，仍然顯示「無法載入學習指引內容」。
   改成只在「使用者已經確定要看這一章」時才抓（直接開該章，或點下連結的那一刻）。實測：滑鼠移上連結後章節資料請求數為 0；點下後章節資料與頁面程式同一刻開始下載，各只請求一次。
2. 圖卡清單的 key 格式檢查原本在寫完 `guideImages.json` 之後才做，格式異常時會留下「總檔已更新、每章檔沒更新」的不一致。改成寫任何檔之前先檢查。

### 已知限制（這一輪沒有處理）

- **第一輪的「滑鼠移上或手指按下連結時預先下載頁面程式」有同一類風險**：預先下載那一刻若請求失敗，之後點進學習指引／公告試題／練習頁會進入錯誤畫面，要按「重新整理」才恢復。發生條件很窄（失敗剛好落在移上連結的那一刻、之後網路又恢復），而且改動前點擊當下若失敗也是同樣結果。換來的好處是第一次進這三類頁面稍快（估計 0.1–0.3 秒，沒有單獨量過）。要不要拿掉由使用者決定。
- 路由頁本身載入失敗進入錯誤畫面時，字型不會啟用，畫面用系統字型顯示。
- 章節代號是 `constructor`、`__proto__` 這類字時會進入錯誤畫面（有重新整理按鈕，不是白屏）。這是既有行為，正常使用不會遇到。
- 內文載入失敗時，錯誤訊息下方會顯示瀏覽器的英文原始訊息。這是既有行為。
- 只在 Chromium 實測，沒有測 Safari、Firefox 與真機。

## 6. 還可以做的（依效益排序，都還沒做）

1. **Render 快取標頭**（第一輪文件第 3 節，要在 Render 後台設定）。設定後回訪者不必每次重新確認程式檔與圖片，是剩下項目裡最划算的一項。
2. **概念圖卡提供小尺寸版本**。圖卡一律是 1792×1024（每張 100–170 KB），手機顯示寬度只有 300 多像素。另外產一份約 800 像素寬的版本並用 `srcset` 讓手機選小圖，手機的圖片流量可以少一半以上，學習指引頁的 LCP 也會跟著下降。要改圖片 pipeline（727 張）。
3. **字型流量**。學習指引頁第一次造訪要下載 25 個字型檔、約 1.4 MB，是整頁最大的一筆流量。可以選擇：改用系統字型（最省，但改變視覺）、減少用到的字重、或自行架設只含常用字的子集。這是視覺決定，需要使用者先選方向。
4. **學習指引頁程式仍有 384 KB**（gzip 64 KB），外加數學公式與 Markdown 解析器約 170 KB（gzip）。沒有數學公式的章節可以不載入公式程式，但要改渲染流程，改動比前面幾項大。
5. PDF 原圖沒有寬高資料，載入時仍會撐開版面。要在 pipeline 輸出寬高欄位，而且 `guideContent` 有整檔雜湊綁定，動之前要先確認影響。
